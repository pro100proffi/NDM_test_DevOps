# Nginx X-Forwarded-For test stand

Тестовый стенд демонстрирует корректную обработку заголовка `X-Forwarded-For` при нескольких `nginx` в режиме reverse proxy.

## Требования задания

1. Есть несколько nginx в режиме обратного прокси.
2. Запрос пользователя может прийти на любой nginx.
3. Запрос может пройти через один nginx или через цепочку из нескольких nginx.
4. Приложение должно получить в `X-Forwarded-For` IP пользователя и всех nginx, через которые прошёл запрос.
5. Приложение не должно получить поддельный `X-Forwarded-For`, который пользователь передал сам.

## Состав стенда

- `nginx1` — доступен с хоста на порту `8081`, IP внутри Docker-сети `172.28.0.11`.
- `nginx2` — доступен с хоста на порту `8082`, IP внутри Docker-сети `172.28.0.12`.
- `nginx3` — доступен с хоста на порту `8083`, IP внутри Docker-сети `172.28.0.13`.
- `app` — Node.js/Express приложение, выводит полученный заголовок `X-Forwarded-For`.

## Принцип решения

Во всех nginx используется общий файл `nginx/xff.inc`.

Логика:

- если запрос пришёл от недоверенного адреса, значит это внешний пользователь, поэтому входящий `X-Forwarded-For` полностью игнорируется;
- если запрос пришёл от доверенного nginx, текущий nginx дописывает свой IP в уже существующий `X-Forwarded-For`;
- доверенными считаются только точные IP nginx-контейнеров: `172.28.0.11`, `172.28.0.12`, `172.28.0.13`.

За счёт этого пользователь не может подложить свой `X-Forwarded-For`, но цепочка между доверенными nginx сохраняется.

## Запуск

```bash
docker compose up --build
```

Остановка:

```bash
docker compose down
```

## Протокол тестирования через curl

Во всех примерах внешний IP пользователя внутри Docker Desktop / Docker bridge обычно отображается как gateway Docker-сети, например `172.28.0.1`. На Linux или другой конфигурации Docker значение может отличаться, но принцип проверки остаётся тем же.

### 1. Пользователь -> nginx1 -> приложение

```bash
curl -s http://localhost:8081/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1"
```

### 2. Пользователь -> nginx2 -> приложение

```bash
curl -s http://localhost:8082/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1"
```

### 3. Пользователь -> nginx3 -> приложение

```bash
curl -s http://localhost:8083/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1"
```

### 4. Пользователь -> nginx1 -> nginx2 -> приложение

```bash
curl -s http://localhost:8081/to-nginx2/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1, 172.28.0.11"
```

### 5. Пользователь -> nginx2 -> nginx3 -> приложение

```bash
curl -s http://localhost:8082/to-nginx3/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1, 172.28.0.12"
```

### 6. Пользователь -> nginx1 -> nginx3 -> приложение

```bash
curl -s http://localhost:8081/to-nginx3/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1, 172.28.0.11"
```

### 7. Пользователь -> nginx1 -> nginx2 -> nginx3 -> приложение

```bash
curl -s http://localhost:8081/to-nginx2-nginx3/ | jq .xForwardedFor
```

Ожидаемо:

```text
"172.28.0.1, 172.28.0.11, 172.28.0.12"
```

### 8. Проверка защиты от поддельного X-Forwarded-For на nginx1

```bash
curl -s -H 'X-Forwarded-For: 8.8.8.8, 1.1.1.1' http://localhost:8081/ | jq .xForwardedFor
```

Ожидаемо: поддельные `8.8.8.8` и `1.1.1.1` отсутствуют.

```text
"172.28.0.1"
```

### 9. Проверка защиты от поддельного X-Forwarded-For при цепочке nginx1 -> nginx2 -> nginx3

```bash
curl -s -H 'X-Forwarded-For: 8.8.8.8, 1.1.1.1' http://localhost:8081/to-nginx2-nginx3/ | jq .xForwardedFor
```

Ожидаемо: поддельные адреса отсутствуют, а цепочка доверенных nginx сохранена.

```text
"172.28.0.1, 172.28.0.11, 172.28.0.12"
```

### 10. Проверка полного JSON-ответа приложения

```bash
curl -s http://localhost:8081/to-nginx2-nginx3/ | jq .
```

Приложение вернёт JSON с полями:

- `xForwardedFor` — итоговый заголовок;
- `remoteAddress` — адрес последнего nginx, с которого приложение получило запрос;
- `allHeaders` — все заголовки, полученные приложением.

## Пример вывода

```json
{
  "receivedBy": "app",
  "path": "/",
  "xForwardedFor": "172.28.0.1, 172.28.0.11, 172.28.0.12",
  "remoteAddress": "::ffff:172.28.0.13"
}
```

Примерное чистое время выполнения: 2–3 часа.
